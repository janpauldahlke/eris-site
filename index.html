[pillars]

Why Eris is different

Sovereign architecture, grammar-disciplined tools, vault-native memory.

Sovereign by architecture

Your vault stays on your machine. Outbound is opt-in.

No telemetry. Your vault is plain Markdown you own. Every outbound integration (web fetch, mail, calendar, Discord) is opt-in and enumerable. The semantic index is derived data; rebuild it anytime from your notes.

Grammar-disciplined tools

No function-calling API required. Token-level GBNF does the work.

Local 8-26B models are sloppy with JSON. Eris compiles GBNF grammars per session, and narrowed per-turn subset grammars, so output is constrained at the token level. 63+ tools pass through one Gatekeeper (JSON Schema + per-state allowlists).

Vault-native memory

The working directory is the vault. Memory is files, not a black box.

Your working directory is the vault. Tiered recall: ephemeral staging (moka), committed notes on disk, semantic search (Qdrant). Prefetch and reindex-on-write keep the agent aligned with what you actually edited.

Why not just Ollama + a chat UI?

Ollama gives you a model. Eris gives you an agent with memory, 63 gated tools, and a vault that's yours. Same local backend, radically different capability ceiling.

[why]

Why I built this

I started Eris by toying around with a local model and a Markdown vault, not a company roadmap. The spark was practical: I wanted a deterministic loop around an LLM (inspired by OpenClaw's idea of a tight, inspectable agent cycle), wired to tools and memory I control.

Two fears pushed me to keep it local. First: if the interesting part of an idea lives only in a hosted chat, it is already halfway someone else's product. Second: if every half-formed thought ships to a cloud log, you start editing yourself. With Eris, nothing leaves the machine unless I flip an opt-in switch, so I can be blunt with the agent about drafts, doubts, and vault chaos.

I am a solo developer. I know projects like Odysseus and Hermes exist in the same space. That is fine. Eris is still the system I run every day, and I would rather share a real codebase under Apache 2.0 than sit on it until it is “perfect.” This is public source: read it, build it, judge it.

If you are also building a local harness: steal the patterns, file issues, or fork. That is the point.

Quickstart (honest)

No one-click install yet. First setup is a focused evening (Rust, llama-server, models, Qdrant). Day two is eris chat.

  • Rust (stable, edition 2024)
  • llama-server + a chat GGUF + an embedding GGUF
  • Docker (for Qdrant semantic memory)
# Qdrant (semantic memory)
docker run -d -p 6333:6333 -v eris-qdrant-data:/qdrant/storage qdrant/qdrant

# Build
cargo build --release
./target/release/eris chat          # first-run wizard
./target/release/eris chat --web    # same session, web UI

docs/REFERENCE.md · llama.cpp setup

Known limitations

  • Alpha; single-user, single-process
  • Installation is manual; installers planned
  • Long-context JSON discipline: improving; benchmark table coming
  • Dogfooded on Linux + NVIDIA; Apple Silicon also supported

What's in the box

Same binary. Different layers of setup.

Layer What When
Always on Chat (TUI + web), vault read/write/list, Gatekeeper + GBNF (llama.cpp), tiered memory (ephemeral + vault + Qdrant), agenda / alarms First eris chat after wizard + Qdrant
Opt-in Web fetch (browser39, allowlist + consent), weather, wiki, Discord sidecar, Google mail/calendar, Moltbook Config flag / credentials
Hardware-gated Vision (vision:see), voice ingress (STT) Multimodal GGUF + mmproj / ffmpeg; ~16 GB VRAM stack

Opt-in and hardware-gated features ship in the same binary. They are not afterthoughts; they are just not required to chat with your vault.

Backend: llama.cpp is the canonical production backend. Ollama is supported as easier install with weaker JSON discipline.

Same SessionEvent / UserAction layer across all surfaces. On each tool turn: GBNF constrains the JSON envelope → Gatekeeper checks state allowlist + schema → tool runs → failures enter Recover with a bounded retry. Memory is always in the loop: vault notes on disk, ephemeral staging for the session, Qdrant for semantic recall. Surfaces stay thin; the orchestrator owns the loop.

Reliability Why small local models still work

Recovery, gatekeeping, an extensible tool roster, and Rust: how the harness stays reliable on 8-26B models.

  1. 01

    Self-healing recovery

    Small models still drift: wrong tool args, tool I/O faults, incomplete turns. Eris treats those as recoverable protocol events, not crashes. A bounded Recover loop feeds the model a concrete correction (what failed, what shape is expected) and retries, capped by max_recovery_attempts. Grammar prevents most malformed JSON; recovery catches what remains.

  2. 02

    Gatekeeper-controlled tools

    Every tool call goes through one gate: state allowlist (Chat / Reflect / Idle / Recover each sees a different set) → arg normalization (common LLM key mistakes) → JSON Schema validation → execute. Operators can enable/disable tool families in config and from the web Tools console.

    The gatekeeper is a protocol boundary for the model, not a security sandbox against a malicious local user.

  3. 03

    A tool roster you can grow

    Out of the box: vault read/write/list, memory stage/commit/query, agenda & alarms, web fetch/search via browser39 (allowlist + consent), weather, wiki, system health, plus optional vision, mail/calendar, Discord. New tools are a first-class extension path: implement the Tool trait, register with the gatekeeper, add a descriptor TOML, allowlist by state. See ADDING_A_TOOL.md. Full roster: TOOLS.md.

    examples [tool] vault:write · memory:query · agenda:remind_at · web:fetch · vision:see

  4. 04

    Rust, on purpose

    One binary. Memory-safe by default: no unsafe, no panics in production paths (? + FcpError). Actor-model concurrency (mpsc, not shared Mutex) keeps the orchestrator responsive under tool rounds. Fast enough for a full-screen TUI and a localhost web console on the same machine as the model.

About What Eris is, and is not · Hardware

Is

  • A Rust reference architecture for sovereign local LLM pipelines: actor model, zero unsafe, zero panics in production paths, single binary
  • The most reliable harness for the GGUF you can run locally: grammar + gatekeeper + recovery, not “smarter model”
  • Smarter about your data than anything hosted: lives where your notes live
  • Extensible: add tools without forking the orchestrator

Is not

  • Smarter than hosted frontier models (intelligence ceiling = your local model)
  • A private ChatGPT replacement (wrong comparison; wrong expectations)
  • A security sandbox (gatekeeper = protocol boundary for the LLM, not anti-malware)

[senses]

Local can see and hear now

Models keep getting better, and the weights you can run at home caught up. Vision and speech are no longer cloud-only tricks.

  • [vision] vision:see on a multimodal GGUF: images from your vault, same gated tool path.
  • [listen] Speech-to-text ingress: talk into the session without shipping audio off-machine.
  • [stack] Gemma 4 12B on 16 GB VRAM is the sweet spot we run: chat + ~32k context + vision headroom.

Vision and voice are hardware-gated: same binary, need the right GGUF stack. Chat, vault, memory, and the tool protocol are always on.
